Redis 분산 락(Distributed Lock)을 사용하는 환경에서 네트워크 단절이나 타임아웃 이후 연결을 다시 사용할 때, 이전 요청의 응답이 다음 요청으로 밀려 들어오는 현상이 발생할 수 있는지 여부는 **기존 TCP 소켓을 실제로 닫고 새로 연결했는지**에 따라 달라진다. 소켓을 완전히 폐기하고 재연결하면 소켓 버퍼도 함께 폐기되므로 응답 밀림은 발생하지 않지만, 타임아웃만 발생한 커넥션을 재사용하면 응답 밀림이 발생하며, 재연결 과정에서도 락 정합성을 깨뜨리는 별도의 문제가 나타난다.

## 1. 응답 밀림(Response Desynchronization) 발생 메커니즘

- **RESP 프로토콜의 FIFO 매칭**: Redis 프로토콜(RESP)은 요청과 응답에 별도의 상관관계 ID(Correlation ID)를 부여하지 않고, 단일 TCP 연결 내에서 **요청을 보낸 순서대로(FIFO) 응답을 매칭**한다.
- **`ReadTimeout` 후 커넥션 재사용**: 클라이언트가 `SET lock:key uuid NX PX 5000` 요청을 전송한 뒤 네트워크 지연이나 Redis 일시 블로킹으로 `SocketTimeoutException(ReadTimeout)`이 발생하면, TCP 연결 자체는 살아 있어 Redis의 `OK` 응답이 뒤늦게 클라이언트 소켓 수신 버퍼에 도착할 수 있다.
- **버퍼 잔여 응답 오독**: 클라이언트가 타임아웃이 발생한 커넥션을 폐기(`close`)하지 않고 커넥션 풀에 반납해 재사용하면, 다음 요청을 보낸 뒤 수신 버퍼에 남아 있던 이전 `OK` 응답을 자신의 결과로 읽어 들인다. 이로 인해 이후 요청들의 응답이 한 칸씩 밀리며 타입 불일치 예외가 발생하거나, 반환 타입이 동일한 경우 타 요청의 성공·실패 결과를 오인하게 된다.
- **클라이언트 구현 차이**: 과거 구버전 Jedis에서 예외 발생 시 커넥션을 풀에 잘못 반납할 때 주로 발생했던 문제이며, 최신 Jedis, Lettuce, Redisson 등 현대적 클라이언트는 타임아웃 및 I/O 예외 발생 시 해당 커넥션을 즉시 폐기하고 새 연결을 맺도록 구현되어 있다.

## 2. 실제 소켓 재연결(Reconnect) 시 발생하는 락 정합성 문제

기존 소켓을 완전히 닫고 새 TCP 연결을 수립하면 응답 밀림은 방지되지만, 분산 락 관점에서는 지연 응답과 유사한 정합성 문제가 발생할 수 있다.

- **연결 단절 중 명령 버퍼링 및 일괄 전송**: Lettuce와 같은 비동기 클라이언트는 기본 `autoReconnect` 설정에서 연결이 끊긴 동안 들어온 명령을 내부 버퍼에 적재했다가 재연결 직후 Redis로 일괄 전송할 수 있다. 애플리케이션 계층에서는 이미 타임아웃·실패로 처리했으나 뒤늦게 락 획득 명령이 실행되어 TTL 동안 점유되는 유령 락이 생기거나, 지연된 해제 명령이 실행될 수 있다.
- **실행 여부 불명확성(Ambiguous Execution)**: 클라이언트의 락 획득 요청은 Redis에 도달해 락이 설정되었으나, 응답 패킷을 수신하기 직전에 연결이 끊어질 수 있다. 클라이언트는 실패로 간주하고 재연결 후 재시도하지만 서버에는 이미 락이 점유되어 획득에 실패하거나, 반대로 작업 완료 후 정상적인 락 해제를 누락할 수 있다.
- **Pub/Sub 알림 누락 및 Watchdog 실패**: Redisson처럼 Pub/Sub으로 락 해제 이벤트를 구독하고 Watchdog으로 TTL을 자동 연장하는 구조에서는, 재연결 구간에 해제 알림을 놓쳐 `waitTime`까지 불필요하게 대기하거나 Watchdog 갱신이 실패해 임계 구역 작업 도중 락이 조기 만료될 수 있다.

## 3. 실무 대응 및 방어 전략

- **예외 커넥션 폐기 및 버퍼링 제어**: 타임아웃이나 네트워크 오류가 발생한 커넥션이 풀에서 재사용되지 않도록 최신 클라이언트를 유지하고, Lettuce 사용 시 재연결 직후 밀린 명령이 한꺼번에 전송되지 않도록 `ClientOptions`의 `disconnectedBehavior(REJECT_COMMANDS)` 설정을 검토한다.
- **소유자 토큰과 원자적 락 해제**: 락 값으로 요청별 고유 식별자(UUID 등)를 저장하고, 락 해제 시 Lua 스크립트로 현재 락의 값이 자신의 토큰과 일치할 때만 삭제하도록 구현해 지연 실행된 해제 명령이 타 요청의 락을 지우는 사고를 차단한다.
- **다중 정합성 보완**: 네트워크 단절 시 서버 반영 여부를 클라이언트가 단정할 수 없으므로, 짧은 TTL 설정과 함께 중요 임계 구역에는 DB 낙관적 락(버전 검증)이나 단조 증가하는 Fencing Token을 병행해 최종 데이터 정합성을 보장한다.
